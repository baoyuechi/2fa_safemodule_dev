## 0. 通用约定（适用于所有页面）

1. **引入模式**：每个被改页面在 supabase-js UMD 与自身内联脚本之后追加一行：
   ```html
   <script src="./mfa/mfa.js"></script>
   ```
   并在创建 client 后一行完成初始化：
   ```js
   ISAMFA.init({ supabase, pageRole: '…' });   // pageRole: 'user' | 'checker' | 'guest'
   ```
2. **回退铁律**（NFR-3）：每处钩子内部首行即判断 `config.ENABLED`，关闭时**行为与改动前逐字节一致**。下文每页的"回退行为"栏即验收这条。
3. **改动量预算**：全部宿主改动合计 ≤30 行（Part 7 M4 的量化验收），末尾 §8 有核算表。
4. 本方案只写"改哪、改成什么"；钩子背后的服务端行为见 Part 4/5，不在此重复。

## 1. H1 · login.html —— 密码兜底登录接管

**现状锚点**：`doLogin()`（53–107 行），成功回调块在 90–93 行：
```js
const username = data.user.user_metadata.username || data.user.email.split('@')[0];
localStorage.setItem('sb_username', username);
alert('登录成功！');
location.href = 'messages.html';
```

**改造**（净增约 4 行）：

a) `<head>` 末尾追加：
```html
<script src="./mfa/mfa.js"></script>
```

b) 51 行 `createClient` 之后追加初始化：
```js
ISAMFA.init({ supabase, pageRole: 'user' });
```

c) 90–93 行成功回调块整体替换为：
```js
const r = await ISAMFA.afterPasswordLogin(data.user);  // 触发风控评估/24h受限/邮箱警告信(服务端)
if (!r.ok) { showError(r.code); return; }              // ISAMFA.errors 中文文案
location.href = r.next;   // 常态: messages.html；未绑定: ./mfa/enroll.html?from=login
```

**语义**：密码通道成功后由模块接管（Part 4 §4.3）——风控评估、受限模式标记、警告信全部在服务端完成，页面只消费 `next`。原 `sb_username` 写入与 alert 一并移除（审计 L-4 的死键顺势清理）。

**回退行为**：`afterPasswordLogin` 在 ENABLED=false 时直接返回 `{ok:true, next:'messages.html'}`，页面表现与旧版仅差"没有 alert"。

## 2. H2 · login-messageschecker.html —— 退化为跳转壳

**现状**：完整的重复登录页（Turnstile+signInWithPassword+checkers 校验，55–113 行）。

**改造**（净增 1 行）：`<head>` 内最前插入：
```html
<script>location.replace('./mfa/login-fido.html?role=checker');</script>
```

**语义**：老链接/收藏夹不断（query 保留 `role=checker` 供统一壳分流）；页面其余内容保留但永不执行到——**不删除**，回退时删掉这一行即可整体还原。统一壳侧对 `role=checker` 的处理：登录成功后追加 checkers 白名单校验（原 104–113 行逻辑迁入 SDK）。

**回退行为**：删掉该行 = 原页面完整恢复。

## 3. H3 · register.html —— 注册插桩（域名白名单 + 一次性手机验证）

**现状锚点**：`doRegister()`（81–129 行）；Turnstile token 读取在 97 行；`signUp` 调用块 109–116 行；成功提示 122–124 行：
```js
alert('注册成功！请前往邮箱查收验证邮件，激活后登录。');
location.href = 'login.html';
```

**改造**（净增约 3 行）：

a/b) 同 §0 引入 + `ISAMFA.init({ supabase, pageRole:'guest' })`。

c) 109–116 行 `signUp` 调用块替换为一次 SDK 编排调用：
```js
const r = await ISAMFA.registerFlow({
    email, username, password,
    captchaToken: captchaToken          // Turnstile 组件留在本页，token 由 SDK 从隐藏域读取(97行同源逻辑)
});
if (!r.ok) { errorMsg.textContent = ISAMFA.errors.translate(r.code); errorMsg.style.display='block'; return; }
alert('注册成功！请前往邮箱查收激活邮件。'); location.href = r.next;  // = 'login.html'
```

**语义**：`registerFlow` 内部依次执行 Part 4 §4.2 时序——`check-email-domain`（服务端强制，FR-1.2）→ 内联渲染手机 OTP 卡片（SDK 渲染 UI，不跳页）→ `verify-otp` → 原 `signUp`（携带 captchaToken 与 metadata.username，参数不变）→ `bind-phone`。**原 signUp 的所有参数与行为保持不变**，只是被包进编排。

**回退行为**：`registerFlow` 检测 ENABLED=false 时退化为直接执行原 signUp 调用（SDK 内保存了等价参数模板）。

## 4. H4 · messages.html —— 发帖互动门槛

**现状锚点**：`initAuth()` 791–810 行（守卫，调用点 1074 行）；`postMessage()` 900 行起。

**改造**（净增约 6 行）：

a/b) §0 引入 + init（581 行 createClient 后）。

c) `initAuth()` 末尾 `return true;` 之前插入：
```js
await ISAMFA.syncStatus(user);                       // 拉取 mfa_enrollments 状态(RLS 只读)
ISAMFA.applyInteractionGate();                       // 未绑定: 置灰发帖框+渲染引导卡(FR-8.2)
```

d) `postMessage()` 函数体首行插入：
```js
if (!(await ISAMFA.interactionStatus()).allowed) { ISAMFA.showEnrollPrompt(); return; }
```

**语义**：UI 层门槛（置灰/引导卡）由 c) 建立；d) 是提交瞬间的最终拦截，且服务端发帖路径仍有 RLS/服务端复验（Part 4 §4.12）——前端检查只是体验层，不是防线。

**回退行为**：syncStatus 与 interactionStatus 在 ENABLED=false 时恒返回允许值；applyInteractionGate 不渲染任何东西。

## 6. H6 · checker-pending / approved / deleted —— 审核员强制指纹门禁

**现状锚点**：三页 `checkAuth()` 完全同构（pending 89–95、approved 88–94、deleted 65–71 行），关键段：
```js
currentChecker = checker;
loadList();
```

**改造**（每页净增 1 行，共 3 行）：

a) 三页各加 §0 引入 + `ISAMFA.init({ supabase, pageRole:'checker' })`。

b) `currentChecker = checker;` 之后插入：
```js
if (!await ISAMFA.checkerGate(session.user)) return;  // 无有效指纹因子: 接管页面渲染绑定引导, 不加载列表
```

**语义**：Part 4 §4.10——密码会话即使通过白名单校验也不得进入（决策 A/FR-9.6）。`checkerGate` 返回 false 时由 SDK 接管 `#list` 容器渲染"审核员须绑定指纹"引导页并阻断 `loadList()`。

**回退行为**：恒返回 true。
