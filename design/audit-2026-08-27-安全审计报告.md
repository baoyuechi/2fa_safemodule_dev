## 二、被审系统概况

- 架构：纯静态前端（≈22 个手写 HTML，无框架无构建工具）部署于 Cloudflare Pages；认证与数据全部经浏览器内 supabase-js@2.38.4 直连 Supabase 项目 `bbcnrsktqarvceekrswb`。
- 业务角色：访客 / 登录用户 / 审核员（Checker，白名单表控制）；留言审核状态机 flag 0→1→2→1。
- 已确认外部端点：Supabase REST/Auth/Storage、jsDelivr CDN、Cloudflare Turnstile、`mailto:`。
- 数据资产：用户凭据（GoTrue 托管）、留言含联系邮箱、通知、审核日志、头像图片。

## 三、发现清单

> 严重度定义：🔴 高危=可直接导致账号接管或数据泄露路径敞开；🟠 中危=显著削弱防线或已造成功能失效；🟡 低危=卫生问题/纵深缺失；⚪ 信息=记录备查。

### 🔴 H-1 认证仅有密码单因子，无第二因子

- **位置**：login.html:51-93、register.html:68、login-messageschecker.html:56、forgot/reset 全链。
- **事实**：`signInWithPassword` 为唯一登录途径；全仓库 0 处 TOTP/WebAuthn/OTP/魔法链接代码。Turnstile 只防机器人不防真人攻击者。
- **影响**：撞库、钓鱼、密码复用泄漏 任一成立即账号完全接管；匿名发言机制进一步放大冒名危害。
- **对照整改**：即本 MFA 项目主体（WebAuthn 通行证 + 恢复码 + 风控）。

### 🔴 H-2 授权最终防线（RLS）位于仓库之外且不可证实 ⚠️ *条件项*

- **事实**：全部数据访问持页面内暴露的 anon key 发起；RLS 策略存在于 Supabase 后台，本仓库零证据。所有者口头声明配置无误。
- **影响矩阵**（源码层面只能给条件结论）：RLS 正确→授权链底座成立；RLS 缺失/半配→任何人可用 anon key 直打 REST API 冒充任意 user_id 写留言、改 flag 顶替审核员、拉取用户名单。
- **建议核验动作**（需所有者同意，只读探测约 10 分钟）：① 用 anon key 试读 `checkers` 表 → 应被拒；② 试写 `logs` 伪记录 → 应被拒；③ 未登录试读他人 notifications → 应被拒。

### 🟠 M-1 凭证迁移烂尾：两代 anon key 并存

- **位置**：新版 `sb_publi…` ×4 页（login:50、register:63、forgot-password:47、reset-password:53）；旧版 JWT `eyJhbGci…` ×7 页（messages:580、details:406、checker 三页、messageschecker:39、login-messageschecker:55）。同一项目同一时刻两种格式。
- **影响**：说明变更流程靠人肉复制；旧 key 明文 JWT 有效期至 **2036 年**（exp=2095101186），长期无人轮换治理。

### 🟠 M-2 密码重置链接硬编码旧域名（疑似已在生产断裂）

- **位置**：forgot-password.html:77 `redirectTo:"https://isaspectrum.pages.dev/reset-password"`，而 notice.html:77 声明已迁移至 `isaspectrum.celestivast.com`。
- **影响**：自邮箱点击重置链接很可能落到已停用的 Pages 域名→整个找回密码通道断路；同时演示了"无配置层、值散落 HTML"的结构性病灶。

### 🟠 M-3 页面守卫体系退化为人肉复制，且四份实现互不一致

- **位置与差异**（详见附录 B 对比表）：8 个文件各持一份会话检查；服务端身份复核 `getUser()` 仅 2/7 处调用；`signOut()` 清理仅 messages.html 有；checker 三页 `checkers` 白名单查询均不解构 error（网络故障被误判为"非审核员"踢人）。
- **影响**：守卫覆盖是运气而非机制；未来新增页面极易遗漏；行为不一致使用户困惑、排查困难。

### 🟠 M-4 角色门禁在客户端仅为展示逻辑

- **位置**：checker-pending.html:92 等；login-messageschecker.html:104。
- **事实**："是不是审核员"由浏览器查询后决定是否显示界面；仓库内不存在任何服务端角色判断代码。
- **影响**：真实防护完全寄托于不可见的 RLS（回归 H-2）。设计上应视为"UI 分流器"，不得计入防御。

### 🟡 L-1 安全相关 HTTP 响应头缺失

- **位置**：_headers（全文件 21 行）仅配置缓存策略；无 CSP、HSTS、X-Frame-Options、X-Content-Type-Options、Referrer-Policy。
- **影响**：无 CSP 使注入类漏洞的兜底缺失；无 frame 保护利于点击劫持诱导。

### 🟡 L-2 安全函数五处副本独立演化

- **位置**：`escapeHtml()` 于 checker 三页与 messages/details 各自定义实现（消息渲染主防线）；图片压缩、通知发送、日志写入亦为页间复制。
- **影响**：任一页面忘加或改动不一致即为注入缺口；已被本次扫描证实当前五份内容一致，但无机制阻止漂移。

### 🟡 L-3 客户端密码规则即"规则本身"

- **位置**：register.html `checkPwdRule`（≥8 位+字母数字）、reset-password 同款。
- **影响**：属于 UX 引导；真正的强度策略取决于 GoTrue 服务端设置（不可见）。不应作为安全控制记账。

### 🟡 L-4 存储层无治理约定

- **位置**：`sb_username` 仅 login.html:91 写入，全站无读取，登出不清理；Supabase 会话键由 SDK 自管。
- **影响**：死数据残留演示了缺乏统一状态管理约定——对即将引入"风控状态""设备指纹"等敏感客户端状态的 MFA 模块构成反面教材。

### 🟡 L-5 PWA 缓存策略部分正确

- **位置**：sw.js:15 显式绕过 supabase.co（✅ 正确避免 API 响应进缓存）；但对静态页 cache-first 且版本号手工管理（`isa-spectrum-v1`）。
- **影响**：安全补丁发布后有陈旧缓存窗口期。

### ⚪ I-1 Turnstile 服务端校验状况不可见

token 由前端读取隐藏输入框传入 captchaToken；真正校验发生在 GoTrue 端（项目设置）。仓库内无从证实该开关开启与否（与 H-2 同类的"仓库外防线"问题，但后果较轻——被滥用时表现是注册垃圾而非泄露）。

### ⚪ I-2 审计留痕设计存在且合理

logs 表记录 operator/action/reason/content 快照，approve/reject/delete/restore 四类操作全覆盖（pending:146 等）。👍 但 logs 写入本身经 anon key+RLS 完成，其防篡改性同样依赖 RLS。

### ⚪ I-3 匿名发言的实现约定脆弱

匿名=插入字面量 `"匿名用户"` 作为 username 字符串并在渲染侧推断（messages.html initNicknameSelect）。真实署名仍落库于 user_id——隐私上反而是正确的；但该约定属隐式协议，建议文档化。

## 四、做得对的方面（避免失衡叙事）

1. 密码由 GoTrue 服务端哈希托管，明文不出 HTTPS。
2. 渲染输出统一转义（L-2 虽有多副本隐患，但当前五份实现一致且正确）。
3. 敏感管理操作全套审计日志（I-2）。
4. Service Worker 阻止 API 缓存（L-5 的正确半边）。
5. 上传走 Storage bucket 权限隔离而非裸 URL 直写。
6. 错误提示语言克制，未向用户回显技术细节。
