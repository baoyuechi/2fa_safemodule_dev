# Part 1 · 需求定义书

> 状态：✅ 已确认（2026-08-27，决策记录见第 6 节）
> 读者提示：本文档不谈任何具体技术实现，只回答一个问题——**这个模块要做哪些事，做到什么程度才算做完**。术语出现时都会顺带解释。

---

## 0. 项目背景与现状结论（来自对参考站的分析）

现有网站（isaSpectrum，校园留言板）的全部安全能力目前只有三项：

| 已有能力 | 类比说明 |
|---|---|
| 邮箱+密码登录 | 相当于只有一把门锁，钥匙丢了别人捡到也能开 |
| 人机验证（Turnstile） | 只能挡机器批量注册，不能防真人的账号被盗 |
| 校园通知的站内信 | 与账号安全无关 |

**确认存在的缺口**：密码一旦被撞库（学生在别处网站用了相同密码）、被钓鱼、被猜测，账号即完全失守；留言板支持匿名发言，被盗号的危害会被放大（冒名发布不当内容难以自证清白）。因此本模块的核心使命是：**让"偷到密码"不再等于"拿到账号"**。

---

## 1. 用户角色定义

| 角色 | 说明 | 本模块视角 |
|---|---|---|
| **学生用户**（主要） | 高中生，人手一台带 Touch ID 的专用 MacBook，注册需学校邮箱 | 本模块的主要服务对象与被保护对象 |
| **审核员 Checker** | 现有站内已有的管理员子类（白名单表控制），拥有删帖、封禁等高权限 | 权限越高，被冒用的破坏越大——策略上应受到更强保护 |
| **系统管理员** | 负责 checkers 白名单、处理恢复申诉的人（现实中的老师或站长本人） | 需要"人工兜底通道"：当学生走投无路时的最后手段 |
| **攻击者**（假想敌） | 偷到他人密码的人、捡到/偷到电脑后尝试解锁的人、批量脚本 | 所有需求最终都是为了让他们失败 |

> ✅ 已拍板：审核员**强制**启用指纹认证（见第 6 节决策 A）。进入审核后台若无有效指纹因子，一律先引导绑定，不允许跳过。

## 2. 功能需求清单（编号便于后续追溯验收）

### ⭐ 总原则：验证手段的等级序（项目负责人 2026-08-27 指令）

本模块所有流程遵守同一条铁律——**验证强度排序为：指纹通行证 > 密码**，与 Google 对 Passkey 的定位一致：

1. **指纹通行证是首选、也是底线**：能刷指纹的场景永远不该退回到密码；系统的安全目标不是"密码之上加一道锁"，而是"把密码从主战场上撤下来"。
2. **密码只是兜底通道**：仅用于"这台设备上还没有绑定通行证"的情形（新 Mac 尚未迁移、极少数不支持指纹的环境）。走密码通道的行为本身即被系统视作高风险事件，须叠加额外的确认措施（见 FR-9.2）。
3. **风控升级不允许"反问密码"**：指纹验证成功后再补验密码属于逻辑倒挂（等于用弱手段审讯强手段已完成的证明）。高危情形下，对已通过指纹的用户采取的是"附加独立核验或临时收紧权限"（FR-9.2），绝不用密码复检。

以下各条编号的需求都以该原则为前提。

### FR-1 注册门槛：学校邮箱唯一准入

- FR-1.1 注册邮箱必须属于学校域名（如 `@xxx.fzghs.cn`），其他域名一律拒绝。
- FR-1.2 拒绝必须发生在**服务端**，而不是只靠网页上的提示——因为改网页提示这种事"稍微会一点浏览器操作的学生就能绕过"。类比嵌入式：就像把校验逻辑放在固件里而不是放在外壳按键上。
- FR-1.3 学校域名应当做成**配置项**而非写死，未来换域名或增加教师域（`@xxx.edu.cn`）时不改代码。

### FR-2 注册期一次性手机号验证

- FR-2.1 首次注册时必须验证手机号（收一次性短信验证码），此后该号码仅作存档/恢复用途，**永不参与日常登录**。
- FR-2.2 一个手机号最多绑定一个账号，防止一人批量注册小号。
- FR-2.3 手机号数据仅用于身份核验与找回场景，页面任何地方都不展示完整号码（符合未成年人隐私的保守原则，见 NFR-4）。
- FR-2.4 由于短信依赖运营商且可能在境外号码上不可用，需提供一条**管理员的电话核验备选通道**（例如辅导员线下核对后在后台手工标记"已验证"，见 FR-7）。

### FR-3 密码规则（兜底因子，继续沿用但加固）

- FR-3.1 密码要求 ≥8 位、同时含字母和数字（与现站一致，迁移成本为零）。
- FR-3.2 修改密码、重置密码必须先通过"更强验证"（见 FR-6 恢复流程），防止攻击者拿到已登录会话后一步改密码占领账号。

### FR-4 第二因子：WebAuthn 指纹认证（本模块核心）

> 名词解释：**WebAuthn** 是一套由苹果/谷歌/微软共同支持的网页标准。你可以把它想象成"网页版的设备配对握手协议"：服务器给 MacBook 出一道签名题，MacBook 用 Secure Enclave 芯片里的私钥签出答案——指纹只负责在本地放行这把私钥的使用，**指纹本身和私钥都永远不会上传服务器**。所以哪怕网站的数据库整个泄露，攻击者也拿不到任何可用于伪造登录的东西。

- FR-4.1 学生应在完成注册/首次登录后**主动引导**绑定指纹：屏幕弹出"接下来用 Touch ID 完成设置"，全程 ≤30 秒。
- FR-4.2 绑定行为必须绑定到**具体的 Mac 设备**：同一账号可以在多台设备各绑一把指纹（换新 Mac 场景），每台设备一把独立密钥。
- FR-4.3 同一设备的每个浏览器可共享设备级密钥（无需 Chrome 和 Safari 各绑一次）。（实现层择优，Part 3 定案）
- FR-4.4 未绑定指纹的账号进入"受限态"（详见 FR-8 引导策略）。
- FR-4.5 支持随时解绑某台设备（丢电脑场景），解绑必须经过强验证（FR-6）。

### FR-5 日常登录体验：常态只刷指纹

- FR-5.1 已绑定指纹的用户再次访问时，登录页自动列出已保存的通行证，**点击 → 刷指纹 → 进入**，不需要输密码。类比：既有一把常用钥匙插在锁上（绑定关系），开门只需要拇指按一下传感器。
- FR-5.2 不再区分"用户登录/审核员登录"两套入口：模块接管后统一为一个登录页，进去后再按角色分流（现状是两个几乎一样的页面，正好借模块化合并减重）。
- FR-5.3 无 Touch ID 的环境（ChromeBook？公用电脑？老师 Windows 机）降级为"密码 + 站内消息确认/邮箱链接"模式，即外接硬件钥匙（YubiKey）类也天然兼容——WebAuthn 标准自带多认证器支持。（细节 Part 3 展开）

### FR-6 恢复体系：三道防线

| 编号 | 场景 | 手段 |
|---|---|---|
| FR-6.1 | 一般预防：怕丢设备 | **静态恢复码**：绑定指纹成功后立即生成 **10 条**（对齐 Google/Microsoft 通行做法）一次性代码，界面提示打印/手抄保存；每条只能用一次 |
| FR-6.2 | 换了新 Mac | 旧设备还在 → 正常登录后自助添加新设备；旧设备没了 → 用任一未使用的恢复码 + 学校邮箱重新进门，进门后立即要求绑定新指纹并撤销其余旧恢复码 |
| FR-6.3 | 设备丢失且怀疑盗用 | 恢复码同 FR-6.2；同时提供**一键挂起**：从任意浏览器发起后冻结所有设备的凭据，等待管理员复核解冻（管理员凭线下身份核对放行，FR-7） |

- FR-6.4 恢复码在数据库中只存哈希值（类似只存指纹的数字摘要，不存原文），即使数据库泄露也无法还原使用。
- FR-6.5 每次恢复码登录，剩余可用数量在通知中心可见提醒；低于 3 条提示重新生成。

### FR-7 管理员兜底通道

- FR-7.1 后台为管理员提供三类操作：① 手工标记学生手机验证状态；② 解除设备绑定/解冻账号（须实名申诉记录）；③ 重置某学生的恢复码。
- FR-7.2 所有管理员兜底操作写入审计日志（复用现站已有的 logs 表设计模式），谁动过谁的账号永远有据可查。

### FR-8 引导策略："不开指纹，只准围观"（类 Steam）

- FR-8.1 未绑定指纹（或等效第二因子）的账号：可以浏览、搜索、看详情、改头像、下载客户端；**不能发帖、不能评论、不能匿名留言、不能修改昵称显示方式**。
- FR-8.2 拦截不是弹警告了事：入口按钮置灰 + 点击弹出引导卡片（"你的账号还差 30 秒的指纹设置即可参与发言"），形成正向推动力。
- FR-8.3 该门槛对现有老用户生效前，提前两周期公告过渡，避免"突然全体禁言"引发舆情。

### FR-9 风控自适应（"大多时候只要指纹"的那颗大脑）

- FR-9.1 定义风险信号（第一期最小集）：① 本次设备此前从未登录过该账号；② 请求来源网络与历史显著不同（校外网络）；③ 极端时段（凌晨 1–5 点）首次使用；④ 最近 24h 内发生过恢复码使用/解绑等敏感事件。
- FR-9.2 默认策略矩阵：

| 命中信号数 | 登录要求 |
|---|---|
| 0 | 只刷指纹（常态目标体验） |
| 1 | 刷指纹成功后，弹出一句确认："这是你本人的操作吗？" |
| ≥2 或命中敏感事件 | 指纹**必须首先通过且不可跳过**（底线）；通过后进入 24h 受限模式：可正常浏览发言，但改密码、绑定新设备、使用恢复码等敏感操作需额外独立核验（学校邮箱确认链接或恢复码），期间所有行为加审计标记 |

> 对照总原则：此矩阵里没有任何一格是"补验密码"——因为对已刷指纹的用户反问密码，等于用弱因子复核强证明。密码通道自身的风控见 FR-9.5。

- FR-9.5 密码通道（兜底）自带两道附加措施，无需等待风控信号：① 成功后立即向学校邮箱发送"新设备/未用指纹登录"警告邮件；② 该会话在 24h 内默认按受限模式处理。若同时命中 ≥2 风险信号，则升级为密码 + 学校邮箱链接双确认才放行。
- FR-9.6 审核员账号走任何通道进入审核后台，都要求存在有效指纹因子并通过指纹验证（决策 A 的延伸：密码登录只进得来普通区域）。

- FR-9.3 规则参数（时段阈值、信任网络记忆时长等）做成配置项，运营期可调。
- FR-9.4 每次风控判定结果写入 risk_events 记录，供管理员复盘"为什么有人突然要多验一次密码"。

## 3. 非功能需求（NFR：做这件事的原则性红线）

| 编号 | 要求 | 说明 |
|---|---|---|
| NFR-1 | **侵入性最低** | 模块以独立文件集合存在，不改现有站的业务代码；参考站两个登录页只需各加一行引入 + 一行钩子调用（Part 2 给出确切位置） |
| NFR-2 | **未成年人数据最小化** | 不收集姓名学号全量身份证件；手机号按 FR-2.3 脱敏展示；密钥、恢复码按 FR-6.4 只存摘要 |
| NFR-3 | **可回退** | 模块整体可通过配置一键关闭，关闭后站点回到"纯密码登录"，原有功能零损伤 |
| NFR-4 | **中文优先 & 低年级友好** | 所有引导文案用高中生能懂的语言，不出现"公钥/质询"这类词（例：不说"注册公钥凭证"，说"让你的 Mac 和校墙互相记住对方"） |
| NFR-5 | **性能感知** | 常态登录（指纹直登）从点击到进入 ≤3 秒；绑定流程触发的资源加载不得拖慢留言板首页 |
| NFR-6 | **审计完备** | 绑定、解绑、恢复、风控升级、管理员操作全部落日志，留存 ≥1 学年 |

## 4. 明确不做的事（边界，防止范围蔓延）

1. ❌ 不做网页内的扫码登录、小程序联动（校内场景收益低）。
2. ❌ 不做短信作为**日常**第二因子（学生校内不带手机，FR-2 只用于注册首验与档案）。
3. ❌ 不做服务端强制全平台重装式的单点登录（SSO）/学籍系统对接（脱离当前权限范围）。
4. ❌ 不改动留言板本身的审核流、匿名机制、通知机制（那些属于原站职责）。

## 5. 验收标准总表

| 需求 | 验收判据（怎么算"做完了"） |
|---|---|
| FR-1 | 用 QQ 邮箱注册被拒；页面拦截与服务端数据库双重体现；换配置后新域名立即可用 |
| FR-2 | 新注册必须收到并输入正确短信码才能建立账号；同号二绑被拒；个人中心只见尾四位 |
| FR-4/5 | Safari 与 Chrome 下：首次绑定 ≤30 秒完成；第二次起打开网站免输密码仅刷指纹进站 |
| FR-6 | 恢复码 10 条各自可用一次且互不重复；正常使用外的连续失败尝试被限速；生成/使用均有日志 |
| FR-7 | 管理员所有操作在 logs 可查，学生侧通知中能看到"管理员执行了什么" |
| FR-8 | 未启用户刷新发帖页：能看帖子、编辑框置灰并有引导卡；绑定完成后实时解除限制 |
| FR-9 | 陌生网络登录触发二级确认；凌晨+新设备命中高危信号时：已刷指纹用户进入受限模式与敏感操作核验（不反问密码）、密码兜底通道被升级为"密码+邮箱链接"；关闭风控开关后回到纯指纹直登 |
